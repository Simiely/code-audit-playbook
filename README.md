# code-audit-playbook · 代码审计方案

> 一套**系统性**的代码审计方案。
> 核心主张：审计靠的不是「读得细」，而是**搜索空间可枚举 + 覆盖率可证明**。
> 目标不是产出一份报告，而是**找到真实根因**，让修复不变成「补丁打补丁」。

---

## 一、为什么需要一套方案

直觉上，审计 = 仔细读代码。但实证研究给出的结论很扫兴：

| 结论 | 来源 |
|---|---|
| 最先进的静态分析器，即便在**最宽松**的评估场景下也只检出约 **53%** 的漏洞；叠加多个工具可再提升 **21~34 个百分点** | [Empirical Study on Static C Code Analyzers](https://mediatum.ub.tum.de/doc/1659728/1659728.pdf) |
| 在真实项目上，静态分析工具的总检出率可能低至 **2.42%** —— 效果高度依赖上下文 | [Effectiveness of Automated Static Analysis Tools](https://cs.colostate.edu/~bieman/Pubs/WedyanAlrumnyBieman.icst09.pdf) |
| 场景/用例驱动阅读比随性阅读、清单阅读高约 **35%** | [Reading Studies III](http://www.cs.umd.edu/class/fall2004/cmsc735/CMSC735%209C%20Experimentation04%20Reading%20Studies%20III.pdf) |
| 清单式阅读 vs 随性阅读：有对照实验发现**两者无显著差异** | [Checklist-based vs Ad Hoc Reading](https://arxiv.org/pdf/0909.4260) |
| 清单 vs 视角式（PBR）的元分析结论矛盾，且「有强烈的**研究者偏差**迹象」 | [What do we know about PBR?](https://ebse.webspace.durham.ac.uk/ebse-bibliography/what-do-we-know-about-perspective-based-reading-an-approach-for-quantitative-aggregation-in-software-engineering/) |
| 用 SAST 告警给**变更函数**排序，审查精度提升 **12%**、召回 **5.6%**，同时省 **13%** 审查量 | [Static Analysis Tools for Secure Code Review](https://ctreude.ca/pdf/an-empirical-study-of-static-2024.pdf) |

**三条推论**：

1. **没有任何单一方法能覆盖大部分问题** → 必须组合。
2. **人工阅读的检出率有硬上限** → 覆盖率的保证只能来自工具。
3. **不同方法找到的是不同的缺陷子集** → 组合才有效。

> 唯一没有争议的两条：① 组合优于单一方法；② Fagan 正式审查的流程纪律有效 —— 定义角色、**发现与修复严格分离**、**修复后必须复检**（专治「坏修复」）。

## 二、方案总览：六层组合

| 层 | 方法 | 解决什么 | 为什么必须在这一层 |
|---|---|---|---|
| **L1 机器枚举 + SAST** | Semgrep / CodeQL / 严格类型 / 架构门禁 | 覆盖率可证明 | 唯一能把「我看过」变成「工具扫过 100%」 |
| **L2 场景驱动阅读** | 走真实用户流程 | **发现没人写下来的隐性规则** | 实证最强的人工方法；补 L1 / L3 的盲区 |
| **L3 已知缺陷类清单** | OWASP ASVS / CWE Top 25 | 已知漏洞类 | 补「不变量」覆盖不到的安全类问题 |
| **L4 执行验证** | 属性测试 / 变异测试 / 畸形输入 | 声明不出来、只能跑出来的问题 | 用执行代替阅读 |
| **L5 根因分析** | 因果链追问三层 | 分离根因与症状 | 决定修复是否「一次到位」 |
| **L6 复检** | 修复后重审改动 | 防止「坏修复」 | 治「补丁打补丁」 |

**关键分工**：L2 是**发现隐性规则**的唯一手段；L1、L3 只能覆盖**已知**的。只做 L1 + L3，会系统性地漏掉「没人想到要写下来的规则」。

---

## 三、三个核心原则

1. **按不变量审，不按文件审** —— 文件是无限的「读法」，不变量是有限的清单。按文件审必然漏，因为你无法证明没漏。
2. **按关注点横扫，不按模块竖读** —— 同一类缺陷出现在同类关注点的**所有**位置。横扫能一次全找出来，而不是修一个、下次再撞见一个。
3. **根因判据** —— **修完它，同类问题不会再出现在别处**；否则就不是根因，是补丁。

---

## 四、怎么用（推荐顺序）

```
① L1 跑工具        → 拿到「机器扫出的清单」（覆盖率可证明）
② L2 走场景        → 拿到「场景走出的清单」（隐性规则）
③ 合并去重         → 形成待验证清单
④ L3 过已知类清单  → 补安全维度
⑤ 逐条做 L5 根因分析 → 把每条从「症状」追问到「结构性缺陷」
⑥ 按根因分类批量修 → 而不是按发现逐条修
⑦ L4 执行验证 + L6 复检 → 确认根因真的修掉了
```

**为什么 ①② 要在 ⑤ 之前**：先穷举搜索空间，再逐条深挖。反过来会变成「抓到一个算一个」。
