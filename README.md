# code-audit-playbook · 代码审计方案

> 一套**系统性**的代码审计方案。
> 核心主张：审计靠的不是「读得细」，而是**搜索空间可枚举 + 覆盖率可证明**。
> 目标不是产出一份报告，而是**找到真实根因**，让修复不变成「补丁打补丁」。

---

## 一、为什么需要一套方案

直觉上，审计 = 仔细读代码。但实证研究给出的结论很扫兴：

| 结论 | 来源 | 强度 |
|---|---|---|
| 单一 SAST 工具在**函数级**只对约 **52%** 的真实漏洞提交产生告警（文件级 89%）；组合五个工具达 **78%**，但仍有 **22%** 的提交**五个工具全部无告警** | [Charoenwet et al. 2024（815 个真实漏洞提交）](https://arxiv.org/html/2407.12241) | ★★★ |
| 静态分析对真实漏洞的**漏报率**在 **47–80%** 之间；叠加多个工具可再降低 **21–34 个百分点**，代价是误报上升 | [Lipp et al.](https://dl.acm.org/doi/10.1145/3727967.3756838) | ★★★ |
| 在真实项目上，静态分析工具的**总检出率可能低至 2.42%** —— 效果高度依赖上下文（结论年份 2009，仅作历史参照） | [Wedyan et al. ICST'09](https://cs.colostate.edu/~bieman/Pubs/WedyanAlrumnyBieman.icst09.pdf) | ★★ |
| 按**用例优先级驱动阅读**（UBR），对「关键缺陷」的检出效果与效率均显著优于清单式阅读 —— **三轮对照实验** | [Thelin et al., EMSE 2004](https://fileadmin.cs.lth.se/serg/old-serg-dok/docs-serg/246_EMSE04_Thelin_UBR.pdf) | ★★★ |
| 清单式阅读 vs 随性阅读：有对照实验发现**两者无显著差异**（与上一行**实验口径不同**，不可直接并列） | [Checklist-based vs Ad Hoc Reading](https://arxiv.org/pdf/0909.4260) | ★ |
| 清单 vs 视角式（PBR）的元分析结论**互相矛盾**，且「有强烈的**研究者偏差**迹象」 | [What do we know about PBR?](https://ebse.webspace.durham.ac.uk/ebse-bibliography/what-do-we-know-about-perspective-based-reading-an-approach-for-quantitative-aggregation-in-software-engineering/) | ★ |
| 用 SAST 告警给**变更函数**排序，审查精度提升 **12%**、召回 **5.6%**，同时省 **13%** 审查量 | [Static Analysis Tools for Secure Code Review](https://ctreude.ca/pdf/an-empirical-study-of-static-2024.pdf) | ★★ |
| AI 代码审查：Google 内部 AI 评论**采纳率 42%**（人类 38%），承担约 15% 评论量；Microsoft 150 团队**机械类缺陷逃逸率 −27%**，但**设计/逻辑类无变化** | [ICSE 2025 / 内部数据汇总](https://tmls.nyc/research/review-bottleneck-agent-code) | ★★ |

> **证据强度**：★★★ = 同行评议 / 元分析 / 官方标准，多源一致；★★ = 同行评议单点结论或大厂公开内部数据；★ = 二手汇总 / 厂商自述，**未经复核不得作为结论依据**。

**三条推论**：

1. **没有任何单一方法能覆盖大部分问题** → 必须组合。
2. **人工阅读的检出率有硬上限** → 覆盖率的保证只能来自工具。
3. **不同方法找到的是不同的缺陷子集** → 组合才有效。

> 唯一没有争议的两条：① 组合优于单一方法；② Fagan 正式审查的流程纪律有效 —— 定义角色、**发现与修复严格分离**、**修复后必须复检**（专治「坏修复」）。
>
> ⚠️ **引用纪律**：引用任何数字前必须回到原文确认口径 —— 实验对象、样本量、是「单工具」还是「组合」、是「检出率」还是「漏报率」。上表的 53% / 35% 曾经是两个被误用的数字，见 [`CHANGELOG.md`](./CHANGELOG.md) 0.2.0 的修订说明。

## 二、方案总览：十层组合

从「核不核得上」到「先修哪个」，十层各管一段。**L0 是其余九层的前提**。

| 层 | 方法 | 解决什么 | 为什么必须在这一层 |
|---|---|---|---|
| **L0 框定** | 威胁建模 + 不变量清单 + 攻击面枚举 | **不变量从哪来** | 「按不变量审」的前提；没它就证明不了枚举完整 |
| **L1 机器枚举 + SAST** | 枚举 + Semgrep/CodeQL + 严格类型 + 架构门禁 + **依赖与构建** | 覆盖率可证明 | 唯一能把「我看过」变成「工具扫过 100%」 |
| **L2 场景驱动阅读** | 按**用例优先级**走真实用户流程 | **发现没人写下来的隐性规则** | 实证最强的人工方法；补 L1 / L3 的盲区 |
| **L2.5 AI 预审** | LLM 对变更做第一遍过滤 | 机械类缺陷的**低成本第一道筛** | 采纳率已超人类；但误报高、有自审盲区 |
| **L3 已知缺陷类清单** | OWASP ASVS **5.0** / CWE Top 25 **2025** | 已知漏洞类 | 补「不变量」覆盖不到的安全类问题 |
| **L4 执行验证** | 属性/变异测试 + fuzz/sanitizer + **关键路径形式化** | 声明不出来、只能跑出来的问题 | 用执行代替阅读；关键路径才要「零漏报」 |
| **L5 根因分析** | 因果链追问三层 | 分离根因与症状 | 决定修复是否「一次到位」 |
| **L5.5 优先序** | 可达性 + EPSS + CISA KEV + SSVC | **先修哪个** | 检出再全，不分级仍会「修了错的、漏了真的」 |
| **L6 补丁正确性验证** | 复检 + 差分 / 变异验证 | 防止「坏修复」与**过拟合补丁** | 单技术最多识别 53.5% 过拟合，组合可达 93.3% |
| **L7 发布后响应** | 巡检 + 运行期可达性 + 判据统一 | 上线以后才暴露的问题 | SSDF RV 组；把「检测与修复共用判据」制度化 |

**标准版本（2026-10 核对）**：OWASP **ASVS 5.0**（2025-05，345 条 / 17 章，**已移除 CWE 直接映射**）｜OWASP Top 10 **2025**（新增 **A03 软件供应链失效**、**A10 异常条件处理不当**）｜CWE Top 25 **2025**。

**关键分工**：

- **L0 决定「审什么」** —— 没有不变量清单，后面九层都是无源之水。
- **L2 是发现隐性规则的唯一「可复现、可审计」人工手段**；L1、L3 只能覆盖**已知**的。注意：L2.5（AI）已能触及部分语义型缺陷，所以不再是「唯一手段」，而是「唯一**可复现**的人工手段」。
- **L5 管「修对」，L5.5 管「先修哪个」** —— 两者并列，不可互相替代。

## 三、三个核心原则

1. **按不变量审，不按文件审** —— 文件是无限的「读法」，不变量是有限的清单。按文件审必然漏，因为你无法证明没漏。（**不变量清单由 L0 产出**。）
2. **按关注点横扫，不按模块竖读** —— 同一类缺陷出现在同类关注点的**所有**位置。横扫能一次全找出来，而不是修一个、下次再撞见一个。
3. **根因判据** —— **修完它，同类问题不会再出现在别处**；否则就不是根因，是补丁。

## 四、怎么用（推荐顺序）

```
① L0 框定            → 产出「可枚举的不变量清单 + 攻击面清单」（覆盖率的分母）
② L1 跑工具          → 机器扫出的清单（含依赖 / 构建 / 供应链）
③ L2 走场景 + L2.5 AI 预审 → 人工清单 + AI 清单（AI 清单必须先人工复核）
④ 合并去重           → 形成待验证清单
⑤ L3 过已知类清单    → 补安全维度
⑥ 逐条做 L5 根因分析 → 把每条从「症状」追问到「结构性缺陷」
⑦ L5.5 排优先序      → 按可达性 + 利用概率 + 影响，输出「动作」
⑧ 按根因分类批量修   → 而不是按发现逐条修
⑨ L4 执行验证 + L6 补丁正确性验证 → 确认根因真被修掉、补丁没修歪
⑩ L7 发布后巡检与响应 → 上线后持续收敛
```

**为什么 ①②③ 要先穷举、⑥ 才深挖**：先穷举搜索空间，再逐条深挖。反过来会变成「抓到一个算一个」。
