# 横向 C 与闭环

> 横向四条（C1–C4）缺一条，方案**退化成清单**；闭环缺了，方案**只是一次性活动**。
> 内核（十层）见 [`DEVELOPMENT.md`](../DEVELOPMENT.md)，外壳（E1–E5）见 [`docs/外壳.md`](./外壳.md)。
> 证据强度沿用仓库约定：★★★ 同行评议/标准 · ★★ 单点或大厂数据 · ★ 厂商自述/二手（待复核）。

---

## C1 · 审查预算 —— 防止审查退化

人不是无限注意力的机器，审查有硬边界：

- **单次 ≤ ~400 行** —— **经验阈值参考**：方向被 Google 变更中位 **24 行**（约 900 万次审查）印证 ★★★，但「400 行」这个具体数字仅来自单一厂商研究（SmartBear × Cisco：10 个月、2,500 次审查、320 万行）★★，**不当实证阈值**
- **速率 ≤ 300–500 行/小时**；单次 **≤ 60–90 分钟**（超过后检出能力下降）
- **小批次不是礼貌，是机制**：大变更天然诱发「LGTM 式橡皮图章」，检出断崖式下降
- **作者预审**：提交前自审 + 标注，能显著降低缺陷密度

（预算边界同时写进 L2 的关键动作。）

## C2 · 度量与反馈回路 —— 「怎么知道方案在起作用」★ 最实质的横向缺失

没有度量，方案无法回答「闸门到底有没有用」。五个真指标：

| 度量 | 怎么算 | 要点 |
|---|---|---|
| **逃逸率** | 生产首次发现的问题 / 全部发现 | **用事件计数，不用度量预测** —— Krutauz 2020 已证明审查相关度量对发布后缺陷的解释**极不稳定**（去掉反而更好）★★★ |
| **分层 MTTR** | 按严重度、按依赖 vs 自研分别统计 | 单一 MTTR 会掩盖「分诊坏了」而非「修复坏了」；校准基线见 L5.5（50% 修复约 100 天）★★ |
| **覆盖率的「可辩护分母」** | 平台侧生产服务注册表中被扫到的比例 | 分母**不能**来自扫描器「见过的清单」 —— 有案例报 98% 覆盖、实际 40% 生产服务从未被扫 ★ |
| **误报率** | 误报 / 全部告警 | 每条误报都在消耗开发者信任；信任耗尽，真问题会被一起忽略 |
| **修复率** | 关闭 / 新发现 | <1.0 表示积压在增长 |

**反馈回路（闭环的一半）**：度量结果**回流 L0 / L1** —— 哪类问题反复逃逸，就把对应不变量写进 L0、把对应枚举写进 L1。**这是方案从「一次性活动」变成「持续运行」的关键。**

## C3 · 组织与能力 —— 「谁来做、有没有时间做」

- **角色 / 职责 / 专属时间**：OWASP 从业者调查，**>60% 的 champion 类机制停滞首因是「没有专属时间」** ★★ —— **没有专属时间的角色等于没有角色**
- **审查者经验匹配**：优先有该文件经验的人（反馈有用率约 2 倍，Bosu 2015）★★★
- **培训与递补**：BSIMM16（111 家企业）显示高分组 champion:dev ≈ **12.3**、低分组 ≈ **2.7**，且高分组的中央安全团队相对规模反而**更小** ★★（成熟度模型数据，取内部一致性结论，不取绝对分）
- **独立性**：见外壳 E4

## C4 · 反面清单 —— 防止方案变成它批评的东西

调研中最可操作的内容其实是**失败模式**（单一作者整理 ★，作假设生成器）。本方案须自警避免：

`checkbox-quality-gate`（只判严重度、忽略可利用性、豁免永久化）· `signed-but-untrusted`（签了名却无法证明来源）· `policy-engine-without-ownership`（策略无人负责）· `centralized-bottleneck`（评审全堵在一个小团队）· `log-everything-explain-nothing`（堆遥测但无法调查）· `maturity-by-tool-spend`（买更多工具就以为成熟）· `exception-without-decay`（豁免永不复审）· **`framework cosplay`（引用 SSDF/SAMM/SLSA/ASVS 却无法映射到实际动作与证据）**。

> **自警**：本方案引入「外壳 / 横向 / 闭环」后，**最大的风险就是自己变成最后一个**。所以 AGENTS.md 立了「防 cosplay」规则：每个构件必须**挂得上证据、映射得到具体动作**，否则不许写进方案。
> 另：识别「包装」的平均准确率约 **54%**（Bond & DePaulo 2006，206 文档 / 24,483 人），**专家与新手无显著差异** —— 别高估「看出数据源有动机」，靠结构性降权与交叉验证。

## 闭环 · Programme 层 —— 从「一次审计」到「一套审计方案」

ISO 19011 区分「单个审计」与「审计方案（audit programme）」★★★。后者是一段时间内的一组审计，含：

- **排期与频次**：周期性 + 风险触发，而不是「想起才审」
- **重审触发条件**（满足任一即须重审相关范围）：
  - 新依赖（含传递依赖变化）/ 依赖大版本升级
  - 架构变更、核心模块重构
  - 新团队 / 新成员接入
  - 新外部暴露（新端点、新集成、权限变化）
  - 高危 CVE 披露（KEV 命中在用组件）
- **方案自评**：定期用下面的**验收判据五问**检验方案本身

## 闭环 · 反馈回路

见 C2 末段：度量回流 L0 / L1。与 Programme 层合起来，构成「方案持续运行」的两半。

## 验收判据 · 五问

改造完成与否，用一次真实审计检验。方案必须能完整回答：

1. **证据在哪？** —— 每条发现有 `file + function + commit SHA` + 指向 CI 产物
2. **谁审的？** —— 审查者与作者分离；高风险由**有该文件经验的非作者**复核
3. **抽了多少？** —— 抽样方法 + 样本量 + 理由，写得出
4. **抽样局限是什么？** —— 外推边界 + 置信声明，写得出
5. **这次审计证明了什么、不证明什么？** —— 声明边界（外壳 E5），写得出

**五问全答出 → 方案成立；任一答不出 → 方案还只是「一套检查动作」，不是「一次审计」。**
